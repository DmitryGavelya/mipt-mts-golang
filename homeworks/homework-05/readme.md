## Задача 1. i2s (3 балла), папка `i2s/`

Реализуйте в `i2s.go`

```go
func i2s(data any, out any) error
```

Функция заполняет `out` из `data`, а `data` - это то, что возвращает `json.Unmarshal` в переменную типа `any`: `map[string]any` для объектов, `[]any` для массивов, `float64` для чисел, `string` и `bool`. Так работают декодеры конфигов и библиотеки вроде `mapstructure`.

* Поддержите поля типов `int`, `string`, `bool`, вложенные структуры и слайсы. Других типов в тестах нет.
* Ключ в map совпадает с именем поля. Поля, которых нет в данных, остаются как были.
* `out` обязан быть ненулевым указателем. Структуру, переданную по значению, заполнить нельзя: функция получит копию, и изменения до вызывающего кода не дойдут. В этом случае верните ошибку.
* Если тип значения не совпадает с типом поля (строка вместо числа, объект вместо массива и т. п.), верните ошибку, а не паникуйте.

Решение занимает 50–80 строк. Проверка: `go test -race` в папке `i2s`, файл `i2s_test.go` не изменять.

Подсказки:

* Разбирайте значение рекурсивно по `Kind()`: структура и слайс заполняются тем же кодом, что и их элементы.
* Писать можно только в адресуемое значение: `reflect.ValueOf(out).Elem()`.
* Слайс нужной длины создаёт `reflect.MakeSlice(v.Type(), n, n)`, элемент берётся через `Index(i)`, а готовый слайс записывается в поле через `Set`.
* Если непонятно, что лежит в `data`, выведите `fmt.Printf("%T %+v\n", data, data)`.

## Задача 2. Генератор API над Postgres (7 баллов), папка `apigen/`

Напишите генератор `apigen/gen/main.go`. Он запускается директивой из `models/models.go`:

```
go generate ./...
```

Генератор читает переданный файл, находит структуры с комментарием `//gen:api <таблица>` и пишет рядом `<имя>_api.go`. Для `models.go` это `models_api.go` с функциями `RegisterUser` и `RegisterNote`. Точные сигнатуры выведите из `models/api_test.go`. Пока генератор их не породил, тесты пакета `models` не компилируются; так и задумано.

### База

Postgres 17 в Docker, нужен Docker с Compose (`docker compose version`). Из папки `apigen`:

```
docker compose up -d --wait   # поднять и дождаться готовности
docker compose down           # остановить
docker compose exec postgres psql -U hw5   # зайти в psql
```

База слушает `localhost:5432`. Пользователь, пароль и имя базы - `hw5`. Данные лежат в памяти контейнера и пропадают после остановки. Таблицы создавать руками не нужно: каждый тест создаёт себе отдельную схему по `apitest.Schema`, наполняет её и удаляет после себя. Если база у вас в другом месте или порт 5432 занят, задайте строку подключения в `DATABASE_URL`. Если база не запущена, тесты сразу падают с сообщением `нет связи с Postgres`.

### Что генерировать

Для каждой структуры генерируются два обработчика. Колонка берётся из тега `db`, ключ JSON из тега `json`, первичным ключом служит поле с `db:"id"`. Все ошибки отдаются как `{"error": "..."}` через `common.WriteError`.

| Запрос | Ответ |
| :---- | :---- |
| `GET /users` | 200, массив в порядке `id`; пустой результат - `[]`, не `null` |
| `GET /users?name=Ada&email=ada@example.com` | 200, только строки, где все условия выполнены |
| `GET /users/{id}` | 200, объект |
| `GET /users/abc` | 400, `bad id` |
| `GET /users/42`, если строки нет | 404, `not found` |

Фильтры. Параметр запроса называется так же, как колонка в теге `db`; по `id` фильтра нет. Значение сравнивается на равенство, несколько параметров объединяются через `AND`. Как разбирать значение, генератор решает по типу поля из AST:

* `string` - как есть;
* целые (`int`, `int32`, `int64`, ...) - `strconv.ParseInt`; при ошибке 400 `<колонка> must be int`;
* `bool` - `strconv.ParseBool`; при ошибке 400 `<колонка> must be bool`.

Параметр, которого нет среди колонок, даёт 400 `unknown filter <имя>`. Значения фильтров попадают в SQL только плейсхолдерами `$1`, `$2`, ...; в текст запроса вклеиваются лишь имена колонок, которые генератор взял из структуры. Один из тестов передаёт в фильтр SQL-инъекцию.

Требования к сгенерированному файлу:

* первая строка - `// Code generated ... DO NOT EDIT.`;
* `reflect` не импортируется: колонки, SQL и `Scan(&v.ID, &v.Name, ...)` вписаны в код явно;
* код прогнан через `go/format`. `TestGeneratedUpToDate` сравнивает файл с выводом генератора побайтно, поэтому сгенерированный файл руками не правят;
* структуры без `//gen:api` пропускаются.

Ничего не хардкодьте. Если имя структуры, таблицы или колонки попало в генератор строкой, решение неверное, даже если тесты на `User` и `Note` проходят. `TestGeneratorNewType` генерирует API для незнакомой структуры в отдельном пакете и гоняет на нём тот же набор тестов.

Проверка: при запущенной базе `go test -race ./...` в папке `apigen`. Не изменяйте `apitest/`, `common/`, `models/models.go` и `models/api_test.go`. Сгенерированный `models_api.go` коммитится вместе с генератором.

Подсказки:

* Сначала напишите руками `models_api.go` для одной структуры и добейтесь зелёных тестов. Потом превратите его в шаблон: так проще отличить ошибку в логике от ошибки в шаблоне.
* Строки вроде `"name, email"` или `"&v.ID, &v.Name"` проще собрать в Go-коде и передать в шаблон готовыми, чем строить циклами внутри `text/template`.
* Тип поля в AST - `*ast.Ident` с именем типа, как оно написано в исходнике. Как разбирать фильтр, решает генератор; в сгенерированный код попадает только нужная ветка.
* Номер плейсхолдера для очередного фильтра - `len(args)` после добавления значения.
* `encoding/json` превращает nil-срез в `null`.
* Если шаблон породил синтаксически неверный Go, `format.Source` вернёт ошибку. Выведите вместе с ней исходный текст, так быстрее найти место в шаблоне.
